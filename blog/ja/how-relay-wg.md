自宅の NAS から社内のテストマシンへアクセスする場合を考えます。両方はルーターの配下にあり、公開アドレスを持ちません。YAT はまず直接接続を試します。hole punching が失敗した場合、パケットは Edge ノード上の relay に渡ります。Edge は利用者自身がデプロイするサーバーです。

設計を決める要素は三つあります。relay をどの階層に置くか、UDP ポートをいくつ使うか、パケット内容を見られるかです。私たちの relay は転送対象の内容を見られます。これは意図した代償であり、第 4 節で理由を説明します。

## 1. relay を置ける階層

WireGuard の直接接続には、互いのアドレスを知っていることと、到達できる経路があることの二つが必要です。アドレス対応は NAT が作りますが、到達性はネットワーク構成に依存します。symmetric NAT ではポートが一致しないことがあります。CGNAT では、どちら側にも相手から届くアドレスがないことがあります。同じルーター配下の機器同士でも、hairpin forwarding の対応に依存します。直接接続できない場合には relay が必要です。

実用的な選択肢は限られます。

**アプリケーション層に置く。** frp や `ssh -R` は TCP ストリームをつなぎます。たとえば「ローカル 8080 をリモート NAS:5001 へ転送」です。設定は正確ですが、プロキシーは IP を理解しません。サービスを追加するたびに設定が必要で、UDP や他のプロトコルも扱いにくくなります。これは port forwarding であり、ネットワーキングではありません。

**ネットワーク層に置き、中央ノードがテーブルを参照する。** 従来の VPN モデルです。経路をすべて中央へ向け、中央が復号し、ルーティングテーブルを見て転送します。実装は単純ですが、両端が直接接続できる場合でも、すべてのトラフィックが中央を通ります。

**ネットワーク層に置き、relay は復号しない。** Tailscale の DERP や NetBird の relay がこの方式です。WireGuard で暗号化済みのバイト列だけを運び、内容は見えません。relay は接続とメンバーの対応を管理し、UDP を TCP や QUIC にカプセル化することが多く、各パケットをユーザー空間で処理します。標準の `wg` ツールでは調査できません。

**ネットワーク層に置き、relay 自身をメンバーにする。** relay は実際の WireGuard インターフェースを持ち、メンバーはこれを通常の peer として設定します。A から B へのパケットはまず relay へ渡り、relay が復号して通常の IP パケットとして転送します。B は A の鍵で暗号化されたパケットを受け取ります。

私たちは最後の方式を選びました。プライバシーの境界は最も弱いですが（第 4 節）、ポートは一つで済み、暗号化と復号はカーネルに残り、`wg` や `tcpdump` などの標準ツールで調査できます。この選択を決める制約が二つあります。

## 2. 二つの制約

### NAT は「送信元ポートと同じソケットからの応答」だけを受け入れる

A が自宅ルーターの配下にあり、`203.0.113.10:58021` へ送信したとします。ルーターは送信元を `1.2.3.4:57138` に書き換え、このポートが `203.0.113.10:58021` への通信に対応することを記録します。

応答が `203.0.113.10:58021` から来た場合だけ、ルーターはそれを A のポート 57138 へ届けられます。relay が別のポートから返信すると、IP が同じでもルーターはパケットを破棄します。

この規則は厳格です。メンバーごとに relay ポートを作る方式も、転送時に送信元ポートを変える方式も、ここで失敗します。relay は UDP ポートを一つに保つ必要があります。メンバーが送信したポートと同じポートから応答しなければなりません。

### WireGuard は peer の endpoint を学習する

peer に `Endpoint` を設定していても、認証済みパケットが別の送信元から届くと、カーネルはその endpoint を更新します。

この動作こそ NAT traversal を機能させますが、relay にとっては危険です。転送のために一時的な送信元ポートを開くと、メンバーはそのポートを relay のアドレスとして学習します。その後の handshake とデータは、誰も待ち受けていないソケットへ向かい、設定を配り直すまで回復しません。

解決は補正ロジックではありません。relay は、メンバーが期待するアドレスとポートから常に送信することです。結局、UDP ポートは一つになります。

したがって最終形は、実際の WireGuard インターフェースを持ち、ネットワークごとに UDP ポートを一つ使う relay です。handshake、keepalive、データはすべてこのポートを使います。メンバー間のパケット配送はカーネルの転送に任せます。

## 3. 現在の構成

```
   メンバー A                                   Edge（利用者がデプロイ）                          メンバー B
 10.24.0.2                              WG インターフェース wg-yat0-xxx                       10.24.0.3
                                        ネットワーク 10.24.0.0/24、ポート 58021

 A ── Edge の公開鍵で暗号化されたデータ ──→ 58021
                                      │ カーネルが復号: src=10.24.0.2 dst=10.24.0.3
                                      │ カーネルが転送: 宛先はこのインターフェース上
                                      │ WireGuard が送信: AllowedIPs で B を選び、B の鍵で暗号化
 58021 ←──────────────────────────── 同じポートから送信 ──────────────────────────────→ B

 B は 58021 へ返信します。A のルーターはポート対応を認識し、パケットを受け入れます。
```

メンバー側の設定は通常の WireGuard 設定で、peer の種類は二つだけです。

```ini
[Interface]
PrivateKey = <メンバーのローカル秘密鍵。このマシンの外に出ない>
Address    = 10.24.0.2/24

# relay: Edge の公開鍵とポート
[Peer]
PublicKey  = <Edge の公開鍵>
Endpoint   = 203.0.113.10:58021
AllowedIPs = 10.24.0.1/32, 10.24.0.3/32   # Edge 自身 + 直接接続していないメンバー
PersistentKeepalive = 25

# 直接接続済みのメンバー: トラフィックは Edge を経由しない
[Peer]
PublicKey  = <メンバー C の公開鍵>
Endpoint   = 192.168.1.30:51820
AllowedIPs = 10.24.0.4/32
PersistentKeepalive = 25
```

意図している点が二つあります。

relay peer の `AllowedIPs` はネットワーク全体ではなく、`/32` を個別に列挙します。二つのメンバーが直接接続を確立すると、そのアドレスは relay peer から direct peer へ移ります。これにより、各メンバー IP の出口は常に一つになり、二つの peer が同じアドレスを持つことはありません。Edge 自身の `10.24.0.1/32` を残すのは、Edge が起点となるパケットを送信元アドレス検査に通すためです。

`PersistentKeepalive = 25` は NAT 対応を維持します。UDP のタイムアウトはルーターに依存しますが、25 秒は WireGuard でよく使われる値であり、実用上の余裕があります。

Edge 側では、ネットワークごとに独立した WireGuard インターフェース、鍵ペア、サブネットを持ちます。観測ループは 5 秒ごとに、各 peer の学習済み endpoint と最後の handshake 時刻を読み取ります。endpoint の変化は経路選択のためにクライアントへ通知します。handshake が 300 秒成功しないと、その peer はオフラインと判断します。

サブネットはネットワーク作成時に選びます。Edge は自分のインターフェースと既存ネットワークを走査して衝突を避け、`100.64.1.0/24` から `100.65.2.0/24` などの CGNAT 候補を優先し、その後に一般的なプライベート範囲へ下がります。

## 4. relay は平文を見られるか

見られます。

各区間は WireGuard で暗号化されるため、公開インターネット上に平文は流れません。しかし Edge では、パケットは一度復号され、再度暗号化されます。エンドツーエンドのセッションはなく、メンバーから Edge、Edge からもう一方のメンバーという独立した二つのセッションがあります。したがって Edge は内容を見られます。これは trusted relay であり、Tailscale のような ciphertext-only relay ではありません。

この代償が受け入れられる理由は三点です。

- Edge は利用者自身のサーバーで動き、私たちのサーバーではありません。データを見られる可能性は、relay をどこへデプロイするかで決まります。
- メンバーの秘密鍵はローカルに残ります。handshake の相手が別メンバーから Edge に変わるだけで、独自の鍵体系は導入しません。
- relay は直接接続できないトラフィックだけを運びます。直接経路が確立されると relay から外します。通常状態は point-to-point であり、relay は fallback です。

relay に内容を見せたくない要件がある場合は、DERP のような ciphertext-only 方式を選ぶべきです。これは高いセキュリティ要件向けの将来方針であり、現在は実装していません。

## 5. デプロイ時に確認する項目

Edge の設定は短くて済みます。

```yaml
proxy:
  wireguard:
    enabled: true
    relay_enabled: true                # この Edge が転送を担うか
    forwarder_strategy: "kernel"       # kernel（デフォルト）または ebpf
```

ホスト側の三つの条件は、通常は Edge の起動時に設定されますが、デプロイチェックリストに入れる価値があります。

```bash
sysctl net.ipv4.ip_forward                 # 1 であること。0 ではカーネルが転送しない
sysctl net.ipv4.conf.all.rp_filter         # 0 であること
sysctl net.ipv4.conf.wg-yat0-xxx.rp_filter # これも 0。カーネルは大きい方の値を使う
```

既知の制限: relay は Linux と IPv4 のみに対応します。同じ NAT 配下のメンバーは、公開 relay を経由せず LAN の直接接続を優先します。

## 6. まとめ

- relay は普通の WireGuard メンバーであり、ネットワークごとに UDP ポートを一つ使います。
- relay は平文を見られます。信頼の境界は、利用者がデプロイする Edge ホストです。
- カーネル転送は `ip_forward`、`rp_filter`、FORWARD firewall に依存します。次の二本の記事で kernel 実装と eBPF 実装を説明します。
