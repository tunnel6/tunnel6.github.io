家里的 NAS 要访问公司的测试机，两台都在路由器后面，都没有公网地址。YAT 先尝试直连；打洞失败后，把包交给 Edge 节点上的中继。Edge 由你自己部署。

中继跑在哪一层、用几个端口、能不能看到内容，决定了后面整个设计。结论是：我们的中继看得到转发的内容。这是主动接受的代价，原因在第四节。

## 一、中继能放在哪几层

WireGuard 直连需要两个条件：双方知道对方地址，而且网络到得了。地址靠 NAT 映射，可达性则受网络形态限制。对称 NAT 会让端口对不上；运营商级 NAT 下两边可能都没有能进来的地址；同一台路由器后面的机器还要看它是否支持回环转发。这些情况直连不通，就需要中继。

中继放在哪一层，可选项其实不多：

**放在应用层。** 类似 frp、`ssh -R`：告诉代理“本地的 8080 转发到远端的 NAS:5001”，它就把这条 TCP 接起来。配置精确，但不理解 IP。新增服务要加配置，UDP 和其他协议也难处理。这是端口转发，不是组网。

**放在网络层，中心节点查表投递。** 传统 VPN 的做法：所有路由指向中心，中心解密、查路由表、再发出去。实现直接，但所有流量都经过中心，即使两端本来能直连。

**放在网络层，但中继不解密。** Tailscale 的 DERP、NetBird 的 relay 属于这一类：中继只搬运 WireGuard 加密后的字节，看不到内容。代价是中继要维护连接和成员的映射，通常还要把 UDP 封进 TCP 或 QUIC，每个包过一遍用户态；排查时用不了标准 `wg` 工具。

**放在网络层，中继自己是网络里的一个成员。** 中继节点起一个真正的 WireGuard 接口，成员把它配置成普通 peer。A 发给 B 的包先交给中继，中继解密后按普通 IP 转发；B 收到的仍是 A 的密钥加密的包。

我们选了最后一种。它的隐私性最差（第四节会说明），但端口最少，加解密留在内核，排查时能用 `wg`、`tcpdump` 等标准工具。下面两个约束解释了这个选择。

## 二、两个约束

### NAT 只承认"发到哪，就从哪回"

A 在自家路由器后面，它往 `203.0.113.10:58021` 发包，路由器把源地址改成 `1.2.3.4:57138` 转发出去，同时记一笔：57138 这个端口对应的是发给 `203.0.113.10:58021` 的流量。

于是回包只有从 `203.0.113.10:58021` 来，路由器才认得它、把它交给 57138。如果中继换了一个端口回包，哪怕 IP 一样，路由器也不认识，直接丢掉。

这条规则很硬。给每个成员开单独中继端口，或者转发时换源端口，都会在这里断掉。中继只能保持一个 UDP 端口：成员发到哪个端口，回包就从哪个端口出来。

### WireGuard 的对端地址是学出来的，不是配好的

即使你在配置里给 peer 写了 `Endpoint`，内核只要收到一个通过校验的包，就会把这个 peer 的地址更新成该包的真实来源，之后的包都往新地址发。

这也是 NAT 穿透能工作的原因，但对中继是陷阱。如果中继另开临时端口转发，成员会把中继地址更新成这个端口；之后的握手和数据都发到一个没人监听的地方，直到重新下发配置。


解决办法不是补偿逻辑，而是让中继发出的包始终来自成员期望的地址和端口。这仍然回到“只用一个端口”。

所以最终形状是：中继持有真实 WireGuard 接口，一个网络一个 UDP 端口；握手、心跳和业务数据都走这个端口。把包从一个成员送到另一个成员，交给内核转发。

## 三、现在的样子

```
   成员 A                                   Edge（你自己部署）                              成员 B
 10.24.0.2                              WG 接口 wg-yat0-xxx                            10.24.0.3
                                          网段 10.24.0.0/24，端口 58021

 A ── 密文（A 用 Edge 的公钥加密）──→ 58021
                                      │ 内核解密，得到 src=10.24.0.2 dst=10.24.0.3 的明文包
                                      │ 内核转发：查路由，目的地在这个接口上
                                      │ WireGuard 发送：按 AllowedIPs 找到成员 B，用 B 的公钥加密
 58021 ←──────────────────────────── 从同一个端口发出 ──────────────────────────────→ B

 B 回包同样发到 58021，A 的路由器一看端口对得上，收下。
```

成员侧的配置就是标准的 WireGuard 配置，只有两类 peer：

```ini
[Interface]
PrivateKey = <成员本地私钥，不会离开这台机器>
Address    = 10.24.0.2/24

# 中继：Edge 的公钥 + Edge 的端口
[Peer]
PublicKey  = <Edge 公钥>
Endpoint   = 203.0.113.10:58021
AllowedIPs = 10.24.0.1/32, 10.24.0.3/32   # Edge 自己 + 还没直连上的成员
PersistentKeepalive = 25

# 已经直连上的成员：流量不经过 Edge
[Peer]
PublicKey  = <成员 C 公钥>
Endpoint   = 192.168.1.30:51820
AllowedIPs = 10.24.0.4/32
PersistentKeepalive = 25
```

有两点是故意这么写的：

中继 peer 的 `AllowedIPs` 是一个个 `/32` 列出来的，而不是直接写整个网段。哪个成员已经直连上了，它的地址就从这里摘掉、换到自己的 peer 上，没直连的还挂在中继上。这样每条成员 IP 在任何时刻只有一个出口，不会出现两个 peer 都声称自己持有同一个地址。列表里保留 Edge 自己的 `10.24.0.1/32`，是为了 Edge 主动发过来的包能通过源地址检查。

`PersistentKeepalive = 25` 用于保住 NAT 映射。UDP 超时随路由器实现变化，25 秒是 WireGuard 常用值，通常有足够余量。

Edge 侧每个网络有一个独立 WireGuard 接口、一对密钥和一个网段。观察循环每 5 秒读一次内核里 peer 学到的地址和最后一次握手时间；地址变化就上报给客户端参与路径判断，握手超过 300 秒判定成员掉线。

网段在创建网络时计算：扫描 Edge 现有网卡和已有网络，避开冲突子网。候选优先取 `100.64.1.0/24` 到 `100.65.2.0/24` 这些 CGNAT 段，再退到常见私网段。

## 四、中继能看到明文吗

能。

每一段链路都是 WireGuard 加密的，公网上不会跑明文；但包在 Edge 这台机器上会被解密、再重新加密发出去。这里没有一个端到端的加密会话，只有“成员—Edge”和“Edge—另一个成员”两段各自独立的会话，中继在中间拆包再重封。所以 Edge 的主机能看到内容。这是这个方案主动接受的代价，它属于"受信中继"，不是 Tailscale 那种只搬密文的中继。

三点让它在我们这里可以接受：

- Edge 由用户自己部署在自己的服务器上，不是我们的机器。数据会被谁看到，取决于你把自己的中继放在哪。
- 成员的私钥始终留在本地，握手的对端从"另一个成员"换成"Edge"，用的还是标准 WireGuard，没有引入任何私有的密钥体系。
- 中继只承载直连失败的那部分流量。一旦两端打通，这条链路就会被从中继上摘走，常态是点对点，中继是兜底。

如果你的场景要求中继完全看不到内容，应选择前面说的“只搬密文”路线。这是高安全等级场景的演进方向，目前没有实现。

## 五、部署时要确认的东西

Edge 的配置只有几行：

```yaml
proxy:
  wireguard:
    enabled: true
    relay_enabled: true                # 是否承担转发
    forwarder_strategy: "kernel"       # kernel（默认）或 ebpf
```

另外三件事需要在机器上成立，正常情况 Edge 启动时会自己处理，但值得进部署清单：

```bash
sysctl net.ipv4.ip_forward                 # 必须是 1，否则内核根本不转发
sysctl net.ipv4.conf.all.rp_filter         # 必须是 0
sysctl net.ipv4.conf.wg-yat0-xxx.rp_filter # 也必须 0，内核取两者中较大的
```

已知限制：中继只支持 Linux 和 IPv4。同一 NAT 后面的成员优先用局域网地址直连，不绕公网中继。

## 六、结论

- 中继是网络里的普通 WireGuard 成员，一个网络只使用一个 UDP 端口。
- 中继能看到明文；信任边界就是你自己部署的 Edge 主机。
- 内核转发由 `ip_forward`、`rp_filter` 和 FORWARD 防火墙共同决定，后面两篇分别讲 kernel 和 eBPF 实现。
