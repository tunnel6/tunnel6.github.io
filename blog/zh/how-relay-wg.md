家里的 NAS 想访问公司的测试机，两台都在路由器后面，都没有公网地址。YAT 的做法是先想办法让它们直接连通，连不通就把包交给中继。中继跑在 Edge 节点上，而 Edge 是你自己部署的服务器。

中继跑在哪一层、用几个端口、能不能看到内容——这三个问题回答完，剩下的选择基本只有一个。先把结论放这：我们的中继看得到转发的内容，这是主动接受的代价，后面会说为什么可以接受。

## 一、中继能放在哪几层

WireGuard 的直连只依赖一件事：双方都知道对方的地址，而且网络到得了。地址靠 NAT 映射，可达性看运气——对称 NAT 会让端口对不上，运营商级 NAT 下两边都没有能进来的地址，两台机器在同一个路由器后面时又需要路由器支持回环转发。这些情况下直连就是不通，必须有中继。

中继放在哪一层，可选项其实不多：

**放在应用层。** 类似 frp、`ssh -R` 这种：你告诉代理"本地的 8080 转发到远端的 NAS:5001"，它就把这条 TCP 接起来。配置精确、穿透也好，但它不理解 IP。你想访问新的服务就得再加一条配置，跑非 TCP 的东西就更麻烦。这是"端口转发"，不是"组网"。

**放在网络层，中心节点查表投递。** 传统 VPN 的样子：所有人都把路由指向中心，中心解密、查自己的路由表、再从另一个隧道发出去。简单直接，代价是所有流量都必须经过中心，哪怕两端本来能直连。

**放在网络层，但中继不解密。** Tailscale 的 DERP、NetBird 的 relay 是这一类：中继只搬运 WireGuard 加密之后的字节，看不到内容。隐私上最干净。代价是中继要自己维护"哪个连接对应哪个成员"这张表，通常还要把 UDP 塞进 TCP 或 QUIC 里跑，每个包都过一遍用户态；排查问题也不能用 `wg` 命令，得用它自带的私有协议工具。

**放在网络层，中继自己就是网络里的一个成员。** 中继节点起一个真正的 WireGuard 接口，成员把它当成一个普通 peer 来配置。A 发给 B 的包交给中继，中继解密出来，按普通 IP 转发交给 B，B 收到的是一个用 A 的密钥加密的包。

我们选了最后一种。它的隐私性最差（下面第四节会说），但在三件事上最省事：端口只用一个，加解密全部交给内核，出了问题能用 `wg`、`tcpdump` 这些标准工具查。为什么这三件事重要，要看下面两个约束。

## 二、两个约束把方案框死了

### NAT 只承认"发到哪，就从哪回"

A 在自家路由器后面，它往 `203.0.113.10:58021` 发包，路由器把源地址改成 `1.2.3.4:57138` 转发出去，同时记一笔：57138 这个端口对应的是发给 `203.0.113.10:58021` 的流量。

于是回包只有从 `203.0.113.10:58021` 来，路由器才认得它、把它交给 57138。如果中继换了一个端口回包，哪怕 IP 一样，路由器也不认识，直接丢掉。

这条规矩很硬。凡是要"每个成员单独开一个中继端口"或者"转发时用另一个源端口"的设计，都会在这里断掉——不是性能问题，是根本不通。所以中继的端口必须收敛：成员发到哪个端口，回包就得从哪个端口出来。

### WireGuard 的对端地址是学出来的，不是配好的

即使你在配置里给 peer 写了 `Endpoint`，内核只要收到一个通过校验的包，就会把这个 peer 的地址更新成该包的真实来源，之后的包都往新地址发。

这正是 NAT 穿透能工作的原因，但对中继是个陷阱。假设中继转发时用了一个临时端口（比如自己另开一个 socket 发包），成员收到这个包，就把中继的地址记成了那个临时端口，之后的包——包括握手——全发往一个没人听的端口，链路就断了。要恢复只能等成员重新下发一次配置，把地址写回正确的值。

要把这件事做对，办法不是加补偿逻辑，而是让中继发出去的包永远来自成员期望的那个地址和端口——还是回到"只用一个端口"。

两个约束指向同一个形状：中继是一个持有真实 WireGuard 接口的普通成员，一个网络一个 UDP 端口，握手、心跳、业务数据全走这个端口。至于"把包从一个成员送到另一个成员"，那就交给内核的转发逻辑，我们不要自己搬。

## 三、现在的样子

```
   成员 A                                   Edge（你自己部署）                              成员 B
 10.24.0.2                              WG 接口 wg-yat0-xxx                            10.24.0.3
                                          网段 10.24.0.0/24，端口 58021

 A ── 密文（A 用 Edge 的公钥加密）──→ 58021
                                      │ 内核解密，得到 src=10.24.0.2 dst=10.24.0.3 的明文包
                                      │ 内核转发：查路由，目的地在这个接口上
                                      │ WireGuard 发送：按 AllowedIPs 找到成员 B，用 B 的公钥加密
 58021 ←──────────────────────────── 从同一个端口发出 ──────────────────────────────→ B

 B 回包同样发到 58021，A 的路由器一看端口对得上，收下。
```

成员侧的配置就是标准的 WireGuard 配置，只有两类 peer：

```ini
[Interface]
PrivateKey = <成员本地私钥，不会离开这台机器>
Address    = 10.24.0.2/24

# 中继：Edge 的公钥 + Edge 的端口
[Peer]
PublicKey  = <Edge 公钥>
Endpoint   = 203.0.113.10:58021
AllowedIPs = 10.24.0.1/32, 10.24.0.3/32   # Edge 自己 + 还没直连上的成员
PersistentKeepalive = 25

# 已经直连上的成员：流量不经过 Edge
[Peer]
PublicKey  = <成员 C 公钥>
Endpoint   = 192.168.1.30:51820
AllowedIPs = 10.24.0.4/32
PersistentKeepalive = 25
```

有两点是故意这么写的：

中继 peer 的 `AllowedIPs` 是一个个 `/32` 列出来的，而不是直接写整个网段。哪个成员已经直连上了，它的地址就从这里摘掉、换到自己的 peer 上，没直连的还挂在中继上。这样每条成员 IP 在任何时刻只有一个出口，不会出现两个 peer 都声称自己持有同一个地址。列表里保留 Edge 自己的 `10.24.0.1/32`，是为了 Edge 主动发过来的包能通过源地址检查。

`PersistentKeepalive = 25` 是为了保住在 NAT 上的映射。路由器不认识的连接会被超时清掉，25 秒发一个包能让它一直活着；NAT 的 UDP 超时通常在一分钟以上，所以 25 秒有足够余量。

Edge 侧做的事：每个网络一个独立的 WireGuard 接口，各自一对密钥、一个网段；一个每 5 秒跑一次的循环，从内核读出每个 peer 当前学到的地址和最后一次握手时间，地址变了就上报给客户端参与路径判断，握手超过 300 秒没动静就判定成员掉线。

网段不是写死的，是创建网络时根据这台机器现有的网卡算出来的，避开已有子网，优先用 `100.64.x.x/24` 这类运营商级 NAT 的地址段——这块地址本来就不会和真实内网撞上。

## 四、中继能看到明文吗

能。

每一段链路都是 WireGuard 加密的，公网上不会跑明文；但包在 Edge 这台机器上会被解密、再重新加密发出去。这里没有一个端到端的加密会话，只有“成员—Edge”和“Edge—另一个成员”两段各自独立的会话，中继在中间拆包再重封。所以 Edge 的主机能看到内容。这是这个方案主动接受的代价，它属于"受信中继"，不是 Tailscale 那种只搬密文的中继。

三点让它在我们这里可以接受：

- Edge 由用户自己部署在自己的服务器上，不是我们的机器。数据会被谁看到，取决于你把自己的中继放在哪。
- 成员的私钥始终留在本地，握手的对端从"另一个成员"换成"Edge"，用的还是标准 WireGuard，没有引入任何私有的密钥体系。
- 中继只承载直连失败的那部分流量。一旦两端打通，这条链路就会被从中继上摘走，常态是点对点，中继是兜底。

如果你的场景确实要求中继完全看不到内容，那"只搬密文"的中继才是对的做法，也就是前面讲的 DERP 那条路线。我们把它保留为高安全等级场景的演进方向，目前没有实现。

## 五、部署时要确认的东西

Edge 的配置只有几行：

```yaml
proxy:
  wireguard:
    enabled: true
    relay_enabled: true                # 是否承担转发
    forwarder_strategy: "kernel"       # kernel（默认）或 ebpf
```

另外三件事需要在机器上成立，正常情况 Edge 启动时会自己处理，但值得进部署清单：

```bash
sysctl net.ipv4.ip_forward                 # 必须是 1，否则内核根本不转发
sysctl net.ipv4.conf.all.rp_filter         # 必须是 0
sysctl net.ipv4.conf.wg-yat0-xxx.rp_filter # 也必须 0，内核取两者中较大的
```

已知的限制：中继只支持 Linux，只支持 IPv4；同在一个 NAT 后面的两个成员不会绕公网中继一圈，而是靠局域网地址直连（多数家用路由器不支持回环转发，绕公网基本不通）。

## 六、结论

- 中继放在哪一层，相当于选择你愿意多维护什么：要么一套私有的中继协议加上每个包一次用户态搬运，要么一个内核接口加上几项主机配置。我们选了后者。
- NAT 和 WireGuard 的地址学习机制共同要求：一个网络只能有一个端口。端口一旦多起来，链路就是不通，这不是性能问题。
- 把包从一个成员送到另一个成员，内核本来就会做，不需要在用户态搬包。剩下的问题只有一个：怎么让内核肯做。
